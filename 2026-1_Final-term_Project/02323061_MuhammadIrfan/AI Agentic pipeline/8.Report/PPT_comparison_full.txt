[SLIDE 2] WHAT ARE WE DOING? (The Big Picture)
=================================================================

* What is a Roll-to-Roll (R2R) coating machine?
  Think of it like a huge printer: a thin sheet of material rolls from one spool
  to another, and a coating is applied in the middle -- like spreading paint on a
  moving belt. Our machine applies a special chemical coating used in battery or
  electronic manufacturing.

* What data does it produce?
  As the sheet moves through the machine, over 226 sensors record values every
  second -- temperatures in 8 ovens, motor speeds, coating pump flow rates, gap
  widths, and material tensions. Each run produces hundreds of thousands of rows.

* What are we trying to predict?
  We want to predict the coating quality (called GSM -- grams per square metre)
  measured at three points: Zone 1 (10.1 m from start), Zone 3 (38.6 m), and
  Zone 4 (62.8 m). The target column is Address{zone}_zone_data_4.

* Why does prediction matter?
  If we can predict coating quality from sensor readings, we can catch problems
  before the material reaches the quality measurement point -- reducing waste,
  stopping bad batches early, and eventually letting the machine adjust itself.

* What is a "pipeline"?
  A pipeline is a series of automatic steps that run in order, like an assembly
  line for data. Raw sensor data goes in at one end; a trained prediction model
  comes out the other end.

[SLIDE 4] THE PIPELINE -- 7 STAGES OVERVIEW
=================================================================

Raw Sensor Data (InfluxDB CSV)
         |
         v
 Stage 1: TRANSFORM
   Rename PLC codes (D305xxx) to readable names (Address*_zone_data_*)
         |
         v
 Stage 2: SYNCHRONIZE
   Shift each sensor in time based on film travel distance to that sensor
         |
         v
 Stage 3: PARTITION
   Find "steady-state" windows where machine runs at correct speed and coating rate
         |
         v
 Stage 4: FUSION
   Stack all matching windows from different runs into one file per condition
         |
         v
 Stage 5: FILTER
   Remove broken sensors (missing data), stuck sensors (no variation), cheat columns
         |
         v
 Stage 6: INPUT SELECT
   From 60-120 sensors, pick only the 2-10 that actually drive coating quality
         |
         v
 Stage 7: MODEL
   Train 7 model types, tune each, test on unseen data, output best predictor
         |
         v
    Prediction Model + Performance Report


One sentence per stage:
  Stage 1: Converts internal machine address codes into human-readable sensor names.
  Stage 2: Shifts each sensor's time series to align with the film's physical travel time.
  Stage 3: Extracts only stable periods where speed and coating signal are within spec.
  Stage 4: Combines all stable segments sharing the same operating condition.
  Stage 5: Drops bad columns -- too many missing values, constant value, or ID-like.
  Stage 6: Uses statistics and ML to find the small set of sensors that predict quality.
  Stage 7: Trains and compares models, tunes the winner, evaluates on unseen test data.

[SLIDE 10] STAGE 6 -- INPUT SELECTION (The most important stage)
=================================================================

LEE WANTE (Demo) approach:
  Method:             SHAP Top-K selection (TopK = 10)
  Candidate pool:     All sensors upstream of target zone
  How selected:       Small RF (n_estimators=120, max_depth=8) -> SHAP values -> top 10
  Downstream block:   Partial -- excludes same DIST group; not a hard distance gate
  Features selected:  Always exactly 10

YUNSEON BYUN (Updated) approach:
  Method:             Batch Refresh 4-score consensus (final_topk = 15)
  Score 1 (wt=0.15):  Redundancy score (corr-group deduplication)
  Score 2 (wt=0.25):  Univariate = 0.5 * Pearson + 0.5 * Mutual Information
  Score 3 (wt=0.30):  Model = 0.5 * RF importance + 0.5 * SHAP importance
  Score 4 (wt=0.30):  Subset score (forward CV gain, incremental R2)
  Consensus:          0.15*R + 0.25*U + 0.30*M + 0.30*S
  Optuna:             50 trials in 5 batches of 10; scores refreshed after each batch
  Features selected:  Up to 15 by consensus ranking
  Downstream block:   Partial (same as Lee Wante)

AGENTIC AI approach:

  STEP 0 -- Physical Eligibility Check (5 rules):
    Rule 1: Keep only numeric columns
    Rule 2: Remove the target column itself
    Rule 3: Remove ALL Address sensors from the SAME zone as target (24 cols)
    Rule 4: Remove any sensor physically PAST the target zone (see numbers below)
    Rule 5: Sort remaining by distance (upstream-first)

  Rule 4 blocking counts (actual run):
    Zone 1 target at 10.1m -> 101 sensors blocked
    Zone 3 target at 38.6m ->  50-53 sensors blocked
    Zone 4 target at 62.8m ->  1-2 sensors blocked

  STEP 1 -- Stage A (Univariate Screening):
    Keep if ANY of: Pearson |r| > 0.02, Spearman |rho| > 0.02, MI > 0.0005

  STEP 2 -- Stage B (RF Importance, Optuna 15 trials, top 30):
    Runs 15 Optuna trials, each fitting RF and recording importance -> keeps top 30

  STEP 3 -- Stage C (Redundancy removal, |r| > 0.92):
    If two sensors correlated > 0.92, drop the one with lower RF importance

  STEP 4 -- Stage D (Forward selection, gain threshold 0.003, max 20 features):
    Adds sensors one by one, keeps only those improving CV R2 by > 0.003

THE KEY INSIGHT -- Downstream Leakage:

  The base code was using a sensor at 62.8m to predict quality at 10.1m.
  That sensor measures the film AFTER it passes the 10.1m prediction point.

  In real production this is impossible: when you need to predict quality at 10.1m,
  the film has not yet reached the 62.8m sensor. You would need to know the future.

  The broken version selected Address4_zone_data_3 (62.8m) as top feature for Zone 1.
  Rule 4 permanently blocks this. 101 sensors were blocked for Zone 1 alone.

[SLIDE 12] REPRODUCIBILITY -- CAN YOU GET THE SAME ANSWER TWICE?
=================================================================

Why reproducibility matters:
  A result is only trustworthy if running the analysis again gives the same answer.
  Without this guarantee, results cannot be published, audited, or certified.

                    | Lee Wante         | Yunseon Byun          | Agentic AI
--------------------|-------------------|------------------------|---------------------------
Random seed         | RANDOM_SEED=42    | Same                   | RANDOM_SEED=42 everywhere
RF determinism      | random_state=42   | Same                   | Same + n_jobs=1 (critical)
CV determinism      | KFold(seed=42)    | KFold(seed=42)         | Same
Optuna determinism  | TPESampler(s=42)  | seed per batch         | TPESampler + NopPruner
File verification   | None              | None                   | SHA-256 hash per file
Drift detection     | None              | None                   | DRIFT DETECTED + auto-stop
Regime A (stg 0-4) | Not applicable    | Not applicable         | Byte-identical (SHA-256)
Regime B (stg 5-8) | Not applicable    | Not applicable         | Seed-deterministic

Simple explanation of SHA-256:
  SHA-256 is a mathematical fingerprint of a file. If even one character changes,
  the fingerprint completely changes. The pipeline stores fingerprints of every
  output file in manifest_*.json. Second run: recompute fingerprints and compare.
  Match = "reproducible". Mismatch = "DRIFT DETECTED", pipeline stops.

Why NopPruner matters:
  Optuna's default pruner stops unpromising trials early, making trial order depend
  on computer speed. NopPruner forces every trial to complete -- same sequence
  every run, regardless of machine load.

[SLIDE 14] THE KNN FIX -- z3d1u0 CASE STUDY
=================================================================

WHAT HAPPENED (before fix):
  Model comparison selected KNN with n_neighbors=1 as winner.
  n_neighbors=1 means: "find the single most similar training point, return that value."
  This memorises the training data perfectly but fails to generalise.

WHY IT LOOKED GOOD IN CV:
  During cross-validation, every validation point has near-identical neighbours in
  the training folds (same dataset, just split differently). CV R2 = 0.8931.

WHY IT FAILED IN TEST:
  On truly unseen test data, the nearest neighbour may be very different.
  The model memorised, not learned. Test R2 = 0.7452.

SIMPLE ANALOGY:
  Studying for an exam by memorising last year's exact answers.
  Perfect score on last year's practice test.
  Poor score on this year's exam with slightly different questions.

THE FIX APPLIED (2026-06-05):
  Changed minimum n_neighbors from 1 to 3 in Optuna search space.
  Applied in BOTH: 30-trial comparison AND 50-trial extended tuning phases.

BEFORE vs AFTER:

  Metric              | Before fix (n=1)  | After fix (n>=3)  | Improvement
  --------------------|-------------------|-------------------|------------
  n_neighbors chosen  | 1                 | 3                 |
  CV R2               | 0.8931            | 0.8887            | (slight drop, expected)
  TEST R2             | 0.7452            | 0.8983            | +0.153
  CV-to-test gap      | 0.148 (overfitting)| 0.009 (healthy) | Closed
  Status              | DEGRADED          | MATCHED           | Fixed


[SLIDE 15] THE NEAR-CONSTANT PROBLEM -- z4d0u1 CASE STUDY
=================================================================

THE DATA:
  Case:        Zone 4, Slot-Die B off, Unwinder on
  Total rows:  40 (28 training, 12 test)
  Target mean: ~6240 GSM
  Target std:  25.99 GSM
  Target range: 6,185 to 6,294 (only 109 units of variation)
  Variation %: 109 / 6240 = 1.7% -- essentially flat

WHY THIS IS IMPOSSIBLE TO PREDICT:
  When the target barely changes, there is no signal to learn from.
  R2 measures how well you predict the VARIATIONS, not the average.
  With only 12 test points on a nearly flat line, any small random fluctuation
  in those 12 points produces a terrible R2 score.

SIMPLE ANALOGY:
  Predicting the temperature of a thermostat-controlled room (22 degrees +/- 0.5).
  Train on 28 measurements, test on 12. Your model says "always about 22 degrees."
  But R2 measures the +/- 0.5 degree variations -- and your model looks terrible.
  It was the data, not the model, that was the problem.

BOTH PIPELINES FAILED:
  Base code R2 = 0.097   (near-zero -- also nearly failed)
  Agentic test R2 = -0.718  (genuine holdout, even harsher on small sample)

CONCLUSION: This is a DATA problem, not a pipeline problem.

WHAT NEEDS TO HAPPEN:
  1. Collect more coating runs under "Zone 4, Slot-Die B off" conditions
  2. Deliberately vary: pump flow, gap settings, oven temperatures
  3. Target: at least 200 rows with target std > 100 GSM
  4. Until then: exclude z4d0u1 from all performance comparisons


[SLIDE 16] WHERE AGENTIC AI IS BETTER
=================================================================

1. PHYSICAL ELIGIBILITY CHECK (no downstream sensor leakage)

   The base code selected Address4_zone_data_3 (62.8m) as top input for Zone 1
   (10.1m). That sensor measures the film AFTER it passes Zone 1 -- impossible in
   real deployment. Rule 4 blocked 101 such sensors for Zone 1 alone.

   Why it matters: A model with downstream leakage appears accurate in testing but
   fails immediately when deployed on a real machine without access to future data.

2. GENUINE HOLDOUT EVALUATION (honest test score)

   Base code reported CV R2 as the "test score." CV uses the same data for
   training and evaluation (in different folds) -- an optimistic estimate.
   Agentic AI reserves 30% before any analysis and evaluates exactly once.

   Why it matters: You are claiming better accuracy than your model will deliver
   in production if you report CV R2 as your test score.

3. MULTI-MODEL COMPETITION (best model wins per case)

   Base code: always RandomForest. Agentic pipeline: 7 families compared.
   Results: XGBoost won 2 cases, LightGBM won 2 cases, RF won 2 cases, KNN won 1.
   Using only RF would leave up to +1.3% test R2 on the table.

   Why it matters: As coating recipes grow, the best model type may vary.
   Automatic competition ensures the right tool is always used.

4. REPRODUCIBILITY MANIFESTS (same answer every time, auditable)

   Base code: no verification. Any file change silently corrupts results.
   Agentic AI: SHA-256 fingerprint for every output file. Second run compares.
   DRIFT DETECTED if any file changed.

   Why it matters: Results can be audited, shared, and submitted to journals with
   a verifiable proof that the answer is the same every run.

5. AUTO-TUNING PARTITIONING (works on new coating recipes)

   Base code: thresholds tuned for current recipe. New recipe -> zero segments.
   Agentic AI: if 0 segments, derives thresholds from data automatically.
   chosen_params.json records exactly what was used for audit.

   Why it matters: Deploy on a new R2R machine or new coating material without
   any manual threshold adjustment -- enabling autonomous operation.


[SLIDE 17] WHERE BASE CODE IS STILL GOOD
=================================================================

1. EASIER TO UNDERSTAND AND MODIFY

   Jupyter notebook lets researchers run individual cells interactively, examine
   data frames mid-pipeline, and iterate quickly on ideas. A new team member can
   read top-to-bottom without learning CLI infrastructure.

   When base code wins: During research and exploration, when experimenting fast
   matters more than production robustness.

2. BATCH-REFRESH CONSENSUS SCORING

   Yunseon Byun's four-component consensus score (redundancy + univariate + model
   + subset) gives every feature a continuous score from 0 to 1. This is more
   nuanced than the agentic pipeline's binary pass/fail funnel -- some features
   eliminated in Stage C (correlation removal) might still carry unique signal.

   When base code wins: When you want a ranked list of all features, not just
   the final selected set.

3. NO DISTANCE METADATA GAPS

   Both pipelines lack DIST entries for Valve_Exhaust_dry1-8. But the agentic
   pipeline's explicit _DIST_METADATA dictionary makes the gap visible and
   actionable. The base code's implicit filtering does not track which sensors
   have unknown positions -- so the gap is harder to see and fix.

   This is a shared limitation, but the agentic pipeline makes it explicit
   rather than hiding it inside general upstream filtering logic.
