## 1. What I Built

ResearchLens AI exists because of one observation: the most exhausting part of academic research is not the thinking — it is the hours spent reading paper after paper before you can even articulate what question to ask. I built a system that handles that part. Researchers upload their corpus, and a pipeline of seven specialized AI agents reads, compares, and synthesizes the literature to surface evidence-based research gaps — each one backed by a direct citation, each one scored for impact and feasibility. The researcher does not get a summary. They get a prioritized list of directions they can actually interrogate, challenge, and decide on. The system does the synthesis. The researcher does the thinking that matters.

## 2. Architecture & Design Decisions

### 2.1 Multi-Agent Pipeline

I chose a multi-agent architecture over a single monolithic prompt for one reason: accountability. When a single prompt fails, you do not know where it went wrong. When Agent 3 produces a bad gap, you know exactly which prompt to fix and why. Each agent owns one cognitive task and nothing else.

**Agent 1 — Analyzer**  
Reads each paper individually. Extracts key findings, stated limitations, and implied limitations the authors did not acknowledge.

**Agent 2 — Comparator**  
Takes all papers together. Maps agreements, genuine contradictions, and methodologies never combined across papers.

**Agent 3 — Gap Generator**  
Produces evidence-based research gaps. Every gap must cite a direct quote from a specific paper — no citation, no gap.

**Agent 4 — Verifier**  
Acts as adversarial peer reviewer. Assigns confidence scores (1–10) and flags weak reasoning in each gap.

**Agent 5 — Priority Scorer**  
Scores each gap on Impact, Feasibility, and Novelty (1–10 each). Produces a ranked table for researcher decision-making.

**Agent 6 — Trend Analyzer**  
Identifies rising trends, saturated areas, and emerging opportunities across the corpus. Runs on demand.

**Agent 7 — Chat Agent**  
Answers researcher questions grounded in the full analysis context. The primary human-in-the-loop interface.

---

### 2.2 Why These Patterns

**Multi-agent over single prompt**  
A single prompt that tries to analyze, compare, generate, and verify all at once collapses under its own scope. Splitting the work into agents means each prompt is narrow, testable, and replaceable. When Agent 2 hallucinated contradictions, I rewrote one prompt — not the entire system.

**Evaluation + Self-reflection**  
The Verifier (Agent 4) is the system's self-reflection layer. It receives the Gap Generator's output and attacks it — assigning confidence scores, flagging weak reasoning, and marking gaps as `Confirmed / Questionable / Weak`. Without this layer, the pipeline would hand the researcher whatever the generator produced and call it done. That is not a trustworthy system. The Priority Scorer adds a second independent evaluation pass, giving each gap a quantified score across Impact, Feasibility, and Novelty. Together, these two agents encode what the course called **epistemic taste** — a standard of quality that does not depend on the researcher already knowing what good looks like.

**HITL — Human-in-the-Loop**  
Every automatic action in the system is reversible or low-stakes. Every high-stakes action requires a human. The researcher chooses which papers to upload, reviews every gap before acting on it, and interrogates the reasoning through the Chat interface. There is no "auto-submit" anywhere in the system. This design reflects the Week 14 principle directly: the checkpoint must sit at the moment before the decision, not after.

**Memory**  
Streamlit's `st.session_state` acts as working memory across the session. It lets the Chat Agent reference the full analysis context without re-running the pipeline, and lets the researcher navigate between tabs without losing their work. It is short-term memory — it does not survive a browser refresh, which became a real problem (see Section 4, Failure 1).

**No RAG, No MCP**  
I considered RAG for retrieving related papers automatically, but decided against it. Giving the system the ability to pull papers the researcher did not choose would remove a critical human checkpoint — the decision about what evidence the analysis is based on. That checkpoint belongs to the researcher, not the pipeline.

---

### 2.3 Prompt Engineering as the Real Architecture

The most consequential design decision in the entire project was not the agent structure. It was a single constraint added to the Gap Generator's prompt:

```
"Every gap MUST include a direct quote from a specific paper as its evidence base.
If the model cannot cite a source, it cannot generate the gap."
```

This one line eliminated the vague, generic gaps the system was producing in early testing. It reflects something I learned the hard way: **alignment drift** is best stopped at generation, not caught after the fact. Constraining what the agent is allowed to produce is more reliable than filtering what it already produced.

### 2.4 Infrastructure Resilience

After the 503 crash (see Section 4, Failure 2), the core `_call()` function was redesigned with exponential backoff and jitter:

```python
def _call(prompt: str) -> str:
    max_retries = 5
    base_delay  = 10  # seconds

    for attempt in range(max_retries):
        try:
            response = client.models.generate_content(
                model=MODEL, contents=prompt
            )
            return response.text or "No output generated."

        except errors.ServerError as e:
            if attempt < max_retries - 1:
                wait = base_delay * (2 ** attempt) + random.uniform(0, 3)
                print(f"Retry {attempt + 1}/{max_retries} in {wait:.1f}s...")
                time.sleep(wait)
            else:
                raise Exception("Gemini API unavailable after 5 retries.") from e

        except errors.ClientError as e:
            if "429" in str(e):
                time.sleep(30 + random.uniform(0, 10))
                continue
            raise e
```

The `random.uniform(0, 3)` jitter prevents retry storms — a standard distributed systems technique called **jitter-based backoff**.

## 3. Where the Humans Are in the Loop

The governing principle here is not just "automate the synthesis, never automate the decision" — it is that **humans can intervene at any point in the process**, not only at the end. The system does not wait for the researcher to review a final output. It invites them in continuously.

---

### 3.1 What Happens Automatically

- Extracting text from uploaded PDFs
- Running Agents 1 through 5 sequentially
- Generating trend analysis on demand
- Rendering the Knowledge Map
- Storing session history within the browser session

These are all either reversible or low-stakes. If the Analyzer extracts text incorrectly, the researcher will see it when they review the gaps. No irreversible action happens without a human seeing the output first.

---

### 3.2 What Requires Human Approval Before the Pipeline Runs

**Selecting which papers to upload**  
The researcher defines the corpus. The system cannot retrieve papers on its own — that is intentional. The quality of every downstream output is bounded by the quality of this decision. I did not want to automate it away.

**Choosing the output language**  
A small decision, but it belongs to the researcher. The system injects the language preference into every agent prompt before the pipeline starts.

---

### 3.3 What Triggers Active Human Participation

This is the most important part — and where this system differs from a standard automated pipeline.

**Chat with analysis results — Active Interrogation**  
After the pipeline completes, the researcher does not just read a one-way output. The system provides two modes of interaction:

First, **suggested questions** — four context-aware questions generated from the analysis, helping the researcher engage immediately:

- *"Which gap is most feasible for a PhD student?"*
- *"What methodology fits Gap 1 best?"*
- *"Are there contradictions between the papers?"*
- *"Which gap has the highest novelty score?"*

Second, **a free-text input field** — the researcher can type any question in their own words, unconstrained by preset options. This is where the real human-in-the-loop work happens: asking follow-up questions, challenging specific claims, redirecting the analysis toward their actual research context.

This is not passive review. This is **active interrogation** — the researcher is actively reshaping the output through their own lens. The Chat Agent must answer grounded in the full analysis context, not generate new information outside the uploaded corpus. If an answer fails to hold up under questioning, the researcher knows immediately that the gap behind it does not deserve their trust.

**Reading and validating the Gaps tab**  
Confidence scores from the Verifier are advisory, not authoritative. Every gap needs to be read alongside its cited evidence before being accepted.

**Deciding which gap to pursue**  
The Priority Score table informs but does not decide. The final research direction is always a human call — because the system has no way to know whether a gap is politically viable, institutionally feasible, or actually within the researcher's expertise.

---

### 3.4 Why the Checkpoint Is Where It Is

There is no "Generate Research Proposal" button in this system. That was a deliberate choice. The moment a researcher acts on a gap — writes a proposal, applies for funding, commits to a direction — the stakes become real. That moment must have a human in front of it, not a button.

More importantly: the system does not just wait for the human at the end. It **invites continuous participation** — through Chat, through suggested questions, through the freedom to ask anything at any point. That is the difference between a pipeline with a checkpoint and a genuinely collaborative system.

## 4. The Failures I Saw — And the Lessons

I want to be honest here. There were two real failures during development — not hypothetical edge cases, but things that actually broke during testing and forced me to go back and redesign parts of the system.

---

### Failure 1 — Session State Loss on Page Refresh

**What happened:**  
Midway through testing, I accidentally refreshed the browser. Everything was gone — all the agent outputs, the gap analysis, the priority scores. The entire pipeline had to run from scratch.

It sounds minor until it happens on a slow connection with five papers uploaded. Then it feels like losing an hour of work in one keystroke.

**Root cause:**  
Streamlit's `st.session_state` is in-memory only. It does not persist across page reloads — that is just how Streamlit works by design. I knew this in theory but did not treat it as a real risk until it cost me.

**Fix applied:**  
Added a Session History log that saves a text preview of each completed analysis within the session. It does not survive a refresh, but at least it gives the researcher a record of what was generated before the page reloaded.

**Full fix still needed:**  
Writing results to a local SQLite database or JSON file immediately after each pipeline run completes. This would make results survive any refresh or accidental navigation.

**What the audit trail showed:**  
No structured log existed at the time of the failure. I reconstructed what happened from Streamlit's terminal output. That reconstruction took longer than the fix itself — which is exactly why a proper audit trail matters.

**Lesson:**  
I built the UI before I built the storage layer. That was the wrong order. Persistent storage should be the first infrastructure decision in any stateful application — not something you add after the first data loss reminds you it matters.

---

### Failure 2 — Gemini API 503 Server Overload

**What happened:**  
During live testing with multiple papers, the pipeline crashed mid-run at the Comparator agent. The terminal showed a `503 UNAVAILABLE` error. All the work Agent 1 had done was gone, and the whole pipeline had to restart from the beginning.

This was the most disruptive failure in the entire project. Not because it was technically complex — it was not — but because it was completely invisible until it happened. The system had no way to recover, no way to retry, and no way to tell the user what went wrong in plain language.

**Full error from the audit log:**

```
google.genai.errors.ServerError: 503 UNAVAILABLE.
{
  'error': {
    'code': 503,
    'message': 'This model is currently experiencing high demand.',
    'status': 'UNAVAILABLE'
  }
}

Traceback:
  File "app.py", line 556, in run_pipeline
    comparison = agent_comparator(combined, analysis)
  File "agents.py", line 49, in agent_comparator
    return _call(...)
  File "agents.py", line 10, in _call
    response = client.models.generate_content(...)
```

**Root cause:**  
The original `_call()` function had zero error handling. One failed API call propagated as an unhandled exception and crashed the entire application. There was no retry, no fallback, no graceful degradation — just a hard crash.

**Fix:**  
Replaced the bare API call with an exponential backoff retry loop (see Section 2.4).

**Retry schedule after the fix:**

- Attempt 1 failure → wait ~10 seconds, retry
- Attempt 2 failure → wait ~20 seconds, retry
- Attempt 3 failure → wait ~40 seconds, retry
- Attempt 4 failure → wait ~80 seconds, retry
- Attempt 5 failure → surface a clear error message to the user

**Lesson:**  
External API calls will fail. Treating them as guaranteed is a design flaw, not a runtime edge case. A pipeline that crashes on the second of four agents is worse than a pipeline that never started — it wastes time, wastes API quota, and gives the user no useful information about what went wrong or what to do next.

Retry logic should be the default for any external API call, written on day one — not added after the first production crash reminds you that servers go down.

## 5. Critical Reflection on Management

### 5.1 Leading an AI Workflow vs. Writing a Program

Writing a program means specifying every step. Leading an AI workflow means specifying the intent and constraints, then auditing whether the behavior matches. That shift — from **authoring logic** to **governing behavior** — is harder than it sounds, and I did not fully appreciate it until I was in the middle of it.

The hardest part was accepting that I could not fully predict what any agent would output. A traditional function returns the same output for the same input. These agents do not. Early in the project, I kept trying to fix non-deterministic outputs by making the prompts longer and more detailed. That made things worse. The outputs became more elaborate but not more reliable.

What actually worked was building evaluation layers — the Verifier, the Priority Scorer — that enforced a quality standard regardless of what the generator produced. That is the shift: from trying to control the output to building systems that catch bad output before it reaches the researcher.

The 503 failure added another dimension. Not only is the model's output non-deterministic — the model's *availability* is non-deterministic too. A robust agentic system has to be designed for failure at every layer: logical failure, prompt failure, infrastructure failure. I only understood that after experiencing all three.

---

### 5.2 Where I Would Place More or Fewer Agents

**Agents I would add:**

**Citation Validator** — Cross-checks every quote the Gap Generator cites against the actual PDF text. Right now this validation is implicit in the Verifier's prompt. That is not rigorous enough. A dedicated agent would catch fabricated citations before they reach the researcher — the one failure mode that would genuinely undermine trust in the system.

**Scope Checker** — Runs before the Gap Generator and flags if the uploaded corpus is too heterogeneous to produce meaningful cross-paper analysis. Without this, the pipeline will generate confident-sounding gaps from papers that have no business being compared.

**Agents I would merge:**

**Priority Scorer → into Verifier** — The Priority Scorer could be a second output section in the Verifier rather than a separate API call. The separation adds latency and one additional point of 503 failure risk without adding enough analytical value to justify it as a standalone agent.

---

### 5.3 The Irreplaceable Human Skill

**Domain judgment.**

The system can tell you that a gap exists. It can score how novel it is relative to the uploaded corpus. What it cannot do is tell you whether that gap *matters* — whether the field is ready for it, whether it is institutionally viable, whether you are the right person to pursue it.

Those judgments require someone who understands the sociology of their discipline, not just its literature. That is the line the system cannot cross. Everything before that line is automatable. Everything after it is not. The HITL checkpoint sits exactly there — not because the system runs out of capability, but because the decision that follows requires something the system genuinely does not have.

## 6. What I Would Do Differently

> *Honest reflection. No marketing. The report's value is its candor.*

**1. Persistent storage before any UI feature.**  
Build the storage layer from the beginning. Losing data on a browser refresh is the most user-hostile failure in the current system — and it would have taken two hours to prevent at the start. I built the UI first. That was the wrong order.

**2. Retry logic before the first API call.**  
The 503 crash was entirely preventable. Exponential backoff should be the default for any external API call, written before the first test run — not added after the first production crash. Infrastructure resilience is not an optimization. It is a baseline requirement.

**3. Evaluation-first design.**  
Write the Verifier's evaluation criteria before writing the Gap Generator's prompt. Defining what "good" looks like before generating output produces tighter prompts and more consistent results. I built the generator before I built the evaluator. That was backwards.

**4. Smaller, harder-constrained prompts from the first draft.**  
Early prompts were long and ambitious. The most reliable agents in the final system have the most constrained prompts — specific output formats, explicit prohibitions, mandatory citation requirements. I would apply that discipline from draft one, not after debugging vague outputs.

**5. A structured audit log as a core feature.**  
Every agent call should write a timestamped record to a log file — timestamp, token count, retry count, output summary. Without it, debugging non-deterministic failures is guesswork. The Failure 1 reconstruction proved this. Observability is not optional in an agentic system. It is what makes the system manageable.
